## 手順

1. 前の引き継ぎ書の「目標」と「次の一手」から続ける。進み具合の正典は版計画のステージ行と台帳（`python .claude/ledger.py roadmap <版>`・`issue <ID>`）。
2. ステージごとにコミットする。push は途中ではしない＝目標のステージまで済んだときにまとめて push する（任されている）。
3. 判断が要るときは推測せず、AskUserQuestion で選択肢を出して待つ（人は VS Code か Remote Control から答える）。
4. トークン予算の助言（リレー）が来たら、いまの一手を閉じて**コミットだけ**する（push しない）。台帳と版計画の途中経過を書き、引き継ぎ書を `status: continue` で書いて応答を終える。
5. 目標のステージまで済んだら、コミットして **push** し（前のセッションのコミットもまとめて送る）、引き継ぎ書を `status: done` で書いて応答を終える（リレーはこのセッションを止め、窓を閉じて終わる）。
6. **最後の 1 本**（冒頭に ⚠️ の一言があるとき）＝目標まで届かないまま終わる回。区切りのよい所でコミットする（push しない）。台帳と版計画の途中経過を書き、引き継ぎ書を `status: continue` で書いて「人への報告」の節（届かなかった理由・残り・push していないコミット・人がすること）を埋める。PushNotification で携帯へ一言知らせてから応答を終える（リレーは止まり、人が続きを決める）。目標まで済んだなら 5 に従う。

## 規則

- 目標の外へ出ない。版の節目（a→b・b→RC・RC→正式のステージ）は、引き継ぎ書の goal に明記されたときだけ、書かれた所まで入れる（a→b と b→RC は 2026-09-27、RC→正式は 2026-10-16 のユーザー決定で恒久化）。
  版の節目でも、人の関所 3 つは人に渡す。
  ① b の動作確認（人が zip・インストーラ・同梱文書を触る）＝その手前で done にし、人が確かめる項目を引き継ぎ書に書く。
  ② 独立レビュー（Codex）の指摘の処方＝指摘と評価を並べて AskUserQuestion で聞いて待つ（どれを直すか・どの版へ送るかを自分で決めない）。
  ③ 公開（タグの push・Release の作成＝RC も正式も）＝その手前で done にする。正式の公開の後の工程（/release の 7b＝ロードマップの並べ替え・フェーズB）も入れない＝パネルで人と行う。
- b→RC と RC→正式の done の前に `node tools/qa-hook/release-check.mjs` を走らせ、表示依存の刻印が HEAD で緑であることを出力で確かめる。前のセッションの引き継ぎ書や台帳の「更新した」を根拠にしない（3.8 で誤りが 1 度あった）。赤ならフルスイートを引数なしで回し直す（パスを渡すと刻印を書かない）。
- 引き継ぎ書を書いた後は何もしない（リレーがこのセッションを止めて次を起こす）。
- フルスイートは回さない（コミット前ゲートの範囲だけ）。版の節目の回で /release の工程が求める分は回してよい。
