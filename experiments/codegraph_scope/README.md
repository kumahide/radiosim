# CodeGraph の射程（母数）の実測（2026-08-31）

**新トリガー案①**（[[project-codegraph-evaluation]]・2026-08-14 に置き、2026-08-31 にユーザー指示で実施）
＝**探索中心の作業を実測して、CodeGraph が畳める部分の大きさを先に知る。**
母数が小さければ、導入して A/B（案②）をやるまでもなく答えが出る。

## なぜ「探索の量」ではなく「探索の対象」を測るのか

CodeGraph が索引するのは **Python のソースだけ**。このリポジトリの探索は
`ISSUES.md`（165KB）・`project_roadmap.md`（104KB）・memory を読む側にも大きく割かれており、
**そこには構造的に一切効かない**。⇒ 「探索が何 % か」では答えにならず、
**探索の中で .py を対象にした往復が何 % か**まで割らないと母数が出ない。

## 走らせ方

```
& "$env:RADIOSIM_PYTHON" experiments/codegraph_scope/measure_scope.py
& "$env:RADIOSIM_PYTHON" experiments/codegraph_scope/sample_labels.py   # 分類の標本
```

数え方（畳み方・作業構成の分類）は `tools/token-usage/analyze_usage.py` の
`_fold` / `classify` をそのまま借りる＝**同じ計測を 2 か所に持たない**（B-077）。
記録は `~/.claude/projects/<プロジェクト>/*.jsonl`＝**このマシンのローカル**。

## 測定結果（記録 67 本 / 往復 11,866 / 総入力 2.54B tok・2026-08-10〜08-31）

| | 値 |
|---|---|
| 往復の作業構成 | 実装 20.1% / **探索 35.4%** / レビュー 14.3% / その他 30.1% |
| 探索の呼び出し 4,485 件の対象 | **py 48.1%** / **doc 37.5%** / 不明 11.6% / 両方 2.9% |
| 探索往復の対象 | py のみ **16.7% of 全往復** / doc のみ 13.1% / 混在 5.6% |
| .py 探索のうち**構造の問い**に見える形 | **19.7%**（424 / 2,156） |
| 連続する「py だけの探索往復」の鎖 | 長さ 2 以上が 388 本（最長 19） |
| **⇒ 往復の節約上限（鎖が全部 1 回に畳めたと仮定）** | **1,065 往復＝全往復の 9.0%** |
| Read/Grep が投入した内容 | 3.93M tok＝総入力の 0.15% |

## 読み方（⚠️ ここを外すと数字が独り歩きする）

- **9.0% は上限であって効果ではない。** 「py だけを触った探索往復の連なりが、
  すべて 1 回のグラフ問い合わせに畳める」という最も甘い仮定の値。
- **現実的な取り分はその 1/5 前後**＝.py を触った探索のうち*構造を聞いている*形は
  **19.7%** で、残りは「実装を読むためにファイルを開いた」＝**中身が要るので
  グラフでは代替できない**。⇒ **おおよそ 2% 前後**。
- **doc 側（探索の 37.5%）には原理的に効かない。** このリポジトリで一番大きい読み物
  （`ISSUES.md` / ロードマップ / memory）はソースではない。
- ⚠️ **`0.15%` を「Read/Grep は安い」と読まない。** これは*一度投入した内容*の量で、
  コストの本体は**それを毎往復再送すること**（総入力 ∝ 往復数 × 文脈）。
  2026-07-27 の「最終文脈の 8%」とは分母が違う数字なので、並べて比較しない。
- ⚠️ **分類のラベルは 1 度外した**＝初版は `--include=*.py` と `views/` 直下の grep を
  「不明」へ落とし、py の母数を過小に見せていた（標本 12 件で発見）。
  **`sample_labels.py` で必ず標本を見てから数字を使う**（[[feedback-synthetic-cases-lie]]）。

## 結論

**母数はあるが、CodeGraph が実際に届く部分は小さい（上限 9% / 現実的に 2% 前後）。**
比較対象は④セッション区切りの **56〜62% 減**（[[feedback-token-budget]]・唯一の実測裏づけ）
なので、**桁が 1〜2 つ違う。** ⇒ 案②（導入して A/B）へ進む価値は薄い。

⚠️ **これは「CodeGraph が悪い」ではない。** README 自身が「小規模リポでは得なのはトークンだけ」
と書いており、このリポジトリは向こうのベンチ対象より **2 桁小さい**。**道具ではなく寸法の問題。**

⛔ **2026-08-31・ユーザー決定＝不採用**（原文「現時点ではCodeGraph不採用にします。」）。
**「現時点では」＝永久却下ではない。** 再評価するとしたら変わるのは寸法のほう＝**実装が
数倍になるか、探索の対象が doc からソースへ大きく移ったとき**。その判定はこのスクリプトを
掛け直せば出る＝**次に問われたときも推測で答えない。**

## 付随して測った doc 側（同じ記録・2026-08-31）

CodeGraph が届かない側に何が在るかも測った（「では doc を畳む道具は？」への材料）:

| | 値 |
|---|---|
| Read の結果トークンのうち **doc/md 系** | **58.0%**（1.79M / 3.09M） |
| 上位 3 本＝`ISSUES.md` 529k ／ `project_roadmap.md` 488k ／ `CHANGELOG.md` 204k | doc の **68%** |
| `ISSUES.md` の Read | **236 回すべて部分読み**（全文読みは 0 回・平均 2,240 tok） |
| 同じセッションで**同じ範囲を読み直した**割合 | **0.5%（4 回）** |

- 🔑 **読み直しの無駄は無い**＝キャッシュや「もう読んだ」規律を足しても取り分はゼロ。
  **1 回 1 回が別の場所**で、アクセスそのものが仕事に内在している。
- 🔑 **全文読みも無い**＝`ISSUES.md` は既に節を狙って読んでいる。⇒ **巨大 doc の分割
  （2026-07-27 に −4〜6% と試算して見送り）は、今回の実測で追認された**＝分割しても
  Read は減らない。
- ⇒ **残る余地は「1 回の取得にかかる往復」だけ**＝`Grep` で行番号を探してから `Read` する
  2 段を、台帳の節を直に返す小さな CLI で 1 段にする形（`ISSUES.md` は Read 236＋Grep 162
  ＝約 400 呼び出し）。⚠️ **見込みは 1〜2%** で、ここも桁は変わらない。
