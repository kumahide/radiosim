# ステージ0 の机上試験の手順（RadioSim Field）

2 台の送受信機（A・B）を同軸とアッテネータでつなぎ、実際の測定に入る前に次のことを確かめます。

- 基板からの漏れが無いこと
- 受信レベルの読みが入力に比例し、1 dB 刻みの値が十分に散ること（ディザ）
- 受信率が入力レベルに対してどう落ちるか（打ち切りのしきい値と感度を決める材料）
- 送信電力の設定が出力どおりに効くこと
- 2 台の個体差

測定は両方向（A→B と B→A）で行います。役割はコマンドで入れ替えるので、配線に触らずに両方向を測れます。2 台とも送信と受信の両方の校正値を持つので、現場ではどちらをどちらに使っても構いません。

1 回の机上試験で測る帯域は 1 つです（920 MHz か 2.4 GHz。2 帯域は同時に動かしません）。2.4 GHz も測るときは、同じ手順を帯域を変えてもう 1 回行います。

ステージ0 は 2 回に分けて行います。

- **ステージ0a（手元）**: 読みの形、線形性、ディザ、受信率、個体差を調べます。ここで分かるのは相対的な値だけです。
- **ステージ0b（校正済みの測定器がある場所）**: 2 台の送信出力を測定器で測ります。これで絶対値が決まり、個体ごとの校正ファイルが作れます。

生のデータはすべて残るので、ステージ0b の実測値が分かったら、ステージ0a を測り直さずに計算し直せます。0a と 0b はどちらを先に行っても構いません。

## 機材

| 機材 | 備考 |
|---|---|
| XIAO ESP32C6 ×2 | ファームは `firmware/README.md` の手順で書き込みます |
| U.FL→SMA ピッグテール ×2 | 一度付けたら外しません。この SMA 端が送信出力の基準面です |
| 固定アッテネータ 30 dB ×2 | 大きな入力で受信側が飽和しないようにします |
| ステップアッテネータ（10 dB 刻み 0〜110・1 dB 刻み 0〜11） | 線形性の物差しになります。確度の分かる機械式を使ってください |
| シールドボックス ×2 | 金属缶でも構いません |
| 50 Ω 終端器 ×2 | 漏れの確認に使います |
| SMA ケーブル一式・USB ケーブル ×2・フェライトコア | USB ケーブルは箱の外へ出します |
| （推奨）記録できる温度計・SMA トルクレンチ | |

## 構成

```
[箱A: XIAO-A]─SMA─[30dB]─[30dB]─[ステップ 0-110]─[ステップ 0-11]─SMA─[箱B: XIAO-B]
     │USB                                                                 │USB
     └──────────────────────────── PC ─────────────────────────────────────┘
```

2 台とも USB で PC につなぎます。USB ケーブルが箱の外に出るので、最初の漏れの確認に合格することが前提です。合格しない場合は、送信側を電池で動かして箱に密閉する構成に切り替えてください。その構成では役割の入れ替えを手で行います。

## 別の PC で測るとき

ファームを書き込んだ PC とは別の PC で測る場合の準備です。

### 別の PC に入れるもの

- Windows（机上試験の途中のキー操作に Windows のコンソールを使います）
- Python 3.11 以上
- git
- このリポジトリ一式（`git clone` で取得します）

`record`・`bench run` は、起動時に git からリポジトリのコミットを取り、記録に残します。取れない場合は止まるので、ファイルだけをコピーしたフォルダでは測れません。`apps/field` だけでなく、リポジトリ全体が必要です。

ESP-IDF は、その PC でファームを書き込む場合にだけ必要です。本体アプリの依存（`requirements.txt`）は要りません。

### 持ち出す前（ファームを書き込む PC で）

1. 未コミットの変更が無い状態で、2 台に同じコミットのファームを書き込みます。版が 2 台で違うと、`bench run` は最初の確認で止まります。
2. 2 台に A・B のラベルを貼ります。
3. そのコミットを push しておきます。

### 別の PC で

1. リポジトリを clone し、ファームと同じコミットを checkout します。記録に残るコミットとファームの版がそろいます。
2. リポジトリの直下で依存を入れます。

   ```
   python -m pip install -r requirements-field.txt
   ```

3. 2 台を USB でつなぎ、デバイスマネージャーで COM ポートの番号を確かめます。
4. 次のコマンドが通れば、Python と依存の準備はできています。

   ```
   python -m apps.field.cli bench plan plan.json
   ```

5. 動作確認（下のセクション）で 2 台が動くことを確かめます。
6. このあとはステージ0a の手順どおりに進めます。

### 測るときの注意

- git で管理しているファイルを、その PC で編集しないでください。編集すると、記録に残るコミットの末尾に `-dirty` が付きます。`測定データ`・`校正` のフォルダや、`plan.json`・`ref.json` をリポジトリの中に置いても、`-dirty` は付きません。
- 測定は 1 時間を超えます。PC のスリープと USB の省電力は切っておいてください。USB のポートが閉じると、ボードは再起動します。
- コマンドは、Windows Terminal、PowerShell、VS Code のターミナルなどの通常のコンソールから実行してください。

### データを持ち帰る

- `測定データ/bench-<日時>` のフォルダを、そのまま元の PC へコピーします。生のデータがすべて入っているので、`bench analyze` はどちらの PC でも何度でも実行できます。
- 校正ファイル（`校正/<個体 ID>.json`）は、実際の測定で記録する PC に置いてください。

## 動作確認

机上試験の前に、2 台が動くかを確かめます。人の操作は要りません。アッテネータは 0 dB にしておいてください（配線をつなぐ前に、アンテナを付けて机の上で行っても構いません）。

```
python -m apps.field.cli probe --port-a COM3 --port-b COM4 --root 測定データ
```

2 台の個体 ID とファームの版を読み、役割を入れ替えながら両方向を 10 秒ずつ測って、次の項目を判定します。帯域は `--band 920`（既定）か `--band 2400` で選び、2 台ともその帯域に切り替えてから測ります。

| 項目 | 合格の条件 |
|---|---|
| ファームの版 | リポジトリのコミットと一致する。コミットが違っても、ファームのソースが同じなら合格 |
| 各方向の受信 | 電波での受信率が 90% 以上で、USB の欠けが 0 |
| 受信レベル | 各方向の受信レベルの生値（中央値）が、前回の合格より 6 dB を超えて下がっていない |
| USB の読み取り | 2 台とも CRC 不一致が 0 |

すべて合格すると終了コード 0 を返し、合格しなかった項目があると 1 を返します。受信率の 90% は動作確認のための目安で、ステージ0 のしきい値ではありません。結果は `測定データ/probe-<日時>/probe.json` に残ります。このフォルダは `bench analyze` では判定できません。

受信レベルは、同じ `--root` の下にある動作確認の記録のうち、同じ 2 台（`--port-a` と `--port-b` を入れ替えても同じ組です）・同じ帯域・電力・チャネルで合格した、いちばん新しいものと比べます。向きは個体 ID で揃えます。コネクタやアンテナの根元が浮くと受信レベルは両方向とも同じだけ下がるので、2 方向を見比べても気づけません。前回と比べて見つけるための項目です。比べる記録が無い初回は「・」の行で知らせ、判定には数えません。

- 2 台の置き方（距離・向き・アンテナ）を変えたときは、`--new-baseline` を付けてください。前回と比べずに測り、合格すれば今回が次からの基準になります。
- 6 dB を超えて下がったのに置き方を変えていないなら、下の「アンテナの点検」をしてください。
- 受信が強すぎると、920 MHz（E220）は受信レベルの生値を −256 で返します（飽和）。このときは「⚠️ 受信が強すぎます」の行で知らせ、受信レベルを前回と比べず、その回を次からの基準にもしません（受信率の項目は数えます）。2 台を離すか、アッテネータを入れて測り直してください。`monitor` の行と机上試験の判定にも「飽和 k 件」と出て、その値は平均に入れません。

### アンテナの点検

最初の基準を取る前と、受信レベルの項目が不合格になったときに行います。基準の記録そのものが浮いた接続で取られると、そのあとの比べは役に立ちません。

1. `settings` で片方を TX、もう片方を RX にし、RX のポートを `monitor` で開いて受信レベルを見ます。
2. RX 側のアンテナだけを外します。受信レベルが大きく下がることを確かめます（2.4 GHz では約 45 dB 下がりました）。ほとんど下がらなければ、アンテナを通らずに受けています。
3. アンテナを付け直し、コネクタ（2.4 GHz は U.FL・920 MHz は SMA）とアンテナの根元を順に指で押します。押したときに値が数 dB 以上戻るなら、そこが浮いています。付け直してから、もう一度確かめてください。
4. 役割を入れ替えて、もう片方でも 2〜3 を行います。

2026-10-19 には、2 組目の U.FL かアンテナの根元が浮いていたため、2.4 GHz の受信レベルが 12〜20 dB 低いまま動作確認に合格していました（押すと 12 dB 上がり、そのまま戻りませんでした）。

## 受信を眺める

記録を残さずに、電波が届いているかや受信レベルを確かめたいときは `monitor` を使います。雛形も保存先も要らず、ファイルは何も書きません。

```
python -m apps.field.cli monitor --port COM4
```

設定が届くと、機器の役割・チャネル・ファームの版を 1 行表示し、設定が変わるたびにもう一度表示します。そのあとは 1 秒ごとに、送信機ごとの受信件数、欠け（電波で届かなかった数と USB で落ちた数）、受信レベルの生値の平均と幅、雑音フロアを表示します。TX のポートを開いた場合は、送った件数を表示します。受信レベルは校正を当てていない生値なので、dBm ではありません。終えるときは q か Ctrl+C を押します。

USB の COM ポートに流れているのはバイナリのデータなので、Tera Term などのターミナルソフトで開くと文字化けします。中身を見るときは `monitor` を使ってください。機器の設定を確かめたり変えたりするときは `settings` を使います（`firmware/README.md` の「設定を変える」）。

```
python -m apps.field.cli settings --port COM4 --channel 1
```

## ステージ0a の手順

準備として、Field の依存を入れておきます（リポジトリの直下で実行します）。

```
python -m pip install -r requirements-field.txt
```

始める前に、動作確認に合格していることを確かめてください。

計画を変えたいときだけ、雛形を書き出して編集します。省略すると既定の計画（920 MHz）で測ります。帯域ごとに電力とチャネルの値域が違うので、2.4 GHz の計画は `--band 2400` で書き出します。計画には帯域（`band`）の欄が入ります。

```
python -m apps.field.cli bench plan plan.json
python -m apps.field.cli bench plan plan2400.json --band 2400
```

測定を始めます。

```
python -m apps.field.cli bench run --port-a COM3 --port-b COM4 --root 測定データ
```

帯域は計画の `band` で決まります。`--band` を付けると計画の帯域と照らし合わせ、食い違うとポートを開く前に止まります。計画を省略したときは `--band` の帯域の既定の計画で測ります（`--band` も省略すると 920 MHz）。始めに 2 台をその帯域に切り替えます。

スクリプトが次の順に進めます。画面に指示が出たら、アッテネータを回すか終端器を付け替えて Enter を押してください。`q` を入力すると止まります。止まるまでの記録は残ります。

1. **2 台の確認**: 個体 ID とファームの版を記録します。2 台の版が違う場合は止まります。
2. **漏れの確認**: 2 台の SMA 端に終端器を付けた状態で、両方向とも 1 つも受からないことを確かめます。指示は 2 回（付けるときと外すとき）です。
3. **温め**: 向きを交互に入れ替えながら、受信レベルの平均が落ち着くまで待ちます（最長 30 分）。
4. **粗い掃引**: ステップアッテネータを 0〜110 dB まで 10 dB ずつ変えます。
5. **細かい掃引**: 受信率が落ち始めたステップの前後を 1 dB ずつ変えます。範囲はスクリプトが決めます。
6. **電力の掃引**: 感度から十分に離れた減衰量で、送信電力を切り替えます（既定の計画で 920 MHz は 0〜13 dBm、2.4 GHz は 2〜20 dBm）。減衰量はスクリプトが決めます。
7. **チャネル**: 既定の計画で 920 MHz はチャネル 0・3・6、2.4 GHz はチャネル 1・6・11 で同じ測定をします。

各ステップでスクリプトが両方向を続けて測るので、アッテネータを回す回数は片方向だけ測る場合と同じです（合計 30 回ほど、全体で 1 時間強）。一部のステップだけ測り直すときは `--only coarse,fine` のように指定します。

測り終えたら判定します。何度でもやり直せます。

```
python -m apps.field.cli bench analyze 測定データ/bench-<日時>
```

判定の結果はフォルダの中の `report.md` と `report.json` に残ります。ステージ0a だけでは入力の値が公称（設定した電力と公称の損失から計算した値）になるので、dBm の校正ファイルは作りません。

## ステージ0b の手順

実測値を書くファイルの雛形を作ります。

```
python -m apps.field.cli bench ref ref.json
```

`ref.json` は帯域ごとの節（`"920"` と `"2400"`）に分かれていて、どちらの節も同じ形です。判定のときは、机上試験の帯域の節だけを使います。帯域を分ける前の形（節の無い平らな形）の `ref.json` は読めないので、雛形を作り直して値を移してください。

**送信出力（2.4 GHz）**: TX にした機器に連続送信をさせ、SMA 端の出力を平均電力計で測ります。

```
python -m apps.field.cli cont --port COM3 --ref ref.json
```

機器が RX なら TX に切り替えてから、最も長いフレームを 60 秒（`--seconds` で 1〜600）送り続けます。その間、ファームが報告する送信時間の割合（デューティ）を画面に出します。終わったら測定器の読みを入力すると、バースト中の電力（読み − 10·log10(デューティ)）を `ref.json` の `"2400"` の `tx_output` に足します。測定器がバースト中の電力を直接読めるなら `--reading burst`、SMA 端と測定器の間に減衰器を入れたなら `--pad-db` でその値を指定します。1 Mbps 以外で出たフレームがあったときは、デューティを使えないので書きません。機器は終わると再起動して普段の送信に戻ります。

**送信出力（920 MHz）**: 920 MHz には `cont` がありません。E220 は送信している間を外へ知らせない（AUX ピンが Low の時間は空中に電波が出ている時間と一致しない）ので、デューティを測れないためです。代わりに、普段のパケットのバーストを、バーストを読める測定器で直接測ります。

- 測定器は、スペクトラムアナライザのゼロスパン（RBW は 1 MHz 以上＝500 kHz 幅の LoRa を全部入れる）か、ピーク電力計・時間ゲート付きの電力計です。LoRa は振幅が一定なので、ゼロスパンではバーストが平らな台形に見え、その高さがバースト中の電力です。
- TX は普段どおり 250 ms ごとに送らせたまま測ります（バースト 1 回は 25〜46 ms）。測りたい電力とチャネルには、先に `settings` で合わせます。
- 読みは `ref.json` の `"920"` の `tx_output` に手で 1 行ずつ足します。必須は `device_id`・`power_cdbm`（0.01 dBm 単位）・`channel`・`dbm`（SMA 端の値＝減衰器を入れたならその分を足した値）です。後で追えるように、2.4 GHz の行と同じく `measured_on`・`instrument`・`reading_dbm`・`pad_db` も書いておきます。

バーストを読める測定器が無いときは、データシート §11 の連続波の送信テスト（約 27 ms のバーストを 250 µs おきに繰り返す＝平均電力計の読みの補正は −0.04 dB）を、測定のためだけの使い捨てのファームで出して平均電力計で測ります。この試験の出力が普段の送信と同じである保証はデータシートに無いので、そのファームで普段のパケットと連続波を受信側の RSSI で読み比べ、差が無いことを確かめてから使います。連続波は測定器につないだシールドの中でだけ出します（データシートが電波法に触れうると注意している機能なので、本番のファームには入れません）。

**損失の実測値**: ステップアッテネータを 0 dB にした状態で、A の SMA 端から B の SMA 端までの損失（固定アッテネータ・ケーブル・ステップアッテネータの挿入損の合計）を、その帯域の節の `fixed_loss_db` に書きます。ステップアッテネータの各ステップは、0 dB からの増分の実測値を、`step_attenuator` の `tens`（10 dB 刻みのつまみ）と `ones`（1 dB 刻みのつまみ）に書きます。挿入損は `fixed_loss_db` に入っているので、ステップの値には含めません。書かなかったステップは公称値のまま計算します。

**信号発生器（任意）**: その帯域の信号（2.4 GHz は 11b・1 Mbps、920 MHz は LoRa）を出せる信号発生器があれば、受信側に既知のレベルを直接入れて、その読みを `rx_direct` に書きます。送信側の経由で求めた値と突き合わせるので、もう一方の経路で確かめられます（閉合チェック）。

最後に、判定をやり直して校正ファイルを作ります。

```
python -m apps.field.cli bench analyze 測定データ/bench-<日時> --ref ref.json --calib-dir 校正
```

`校正/<個体 ID>.json` が 2 台分できます。受信の校正値は帯域ごとに、送信出力の表は帯域・電力・チャネルごとの行で持ちます。表の各行には、測定器で直接測った値（`meter`）か、電力の掃引の相対差から導いた値（`bench_power_sweep`）かが書かれています。校正ファイルが既にあれば、机上試験の帯域の分だけを書き換え、もう一方の帯域の分は残します。帯域を分ける前の校正ファイルは、920 MHz の分として読みます。

## 実際の測定での使い方

記録するときに校正ファイルのフォルダを指定すると、雛形に書いた個体 ID で校正ファイルを読み、セッションに写します。雛形に校正値を書く必要はありません。

```
python -m apps.field.cli record --template 雛形.json --port COM5 --root 測定データ --calib 校正
```

受信と送信の校正値は、TX の設定の帯域で選びます。送信側の出力は、実際に動いている帯域・電力・チャネルの行から選ばれます。その行が校正ファイルに無い場合は、記録を始めません。

## 判定の目安

`report.md` には目安との比較が並びます。打ち切りのしきい値、感度、ウィンドウの最小件数を最終的に決めるのは作業者です。

| 項目 | 目安 |
|---|---|
| 漏れ | 終端した状態で 1 つも受からない |
| 線形性 | 線形域での最大のずれが 1 dB 以内 |
| ディザ | 受信率 99% 以上のステップで、読みが 2 種類以上の値に散る |
