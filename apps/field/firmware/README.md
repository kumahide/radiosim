# RadioSim Field ファーム（XIAO ESP32C6 ＋ E220-900T22S(JP)・920 MHz／2.4 GHz）

実測補助ツール（RadioSim Field）の送受信機のファームです。同じファームを 2 台に書き込み、1 台を送信（TX）、もう 1 台を受信（RX）に設定して使います。電波は 920 MHz 帯の LoRa モジュール（E220-900T22S(JP)）か、ESP32C6 の Wi-Fi（2.4 GHz）で送受信します。どちらを使うかは設定で 1 つに決め、起動時にその帯域だけを起こします（2 帯域は同時に動かしません）。920 MHz のとき、ESP32C6 はモジュールの設定と USB とのやり取りを受け持ちます。

- TX は、番号付きのパケットを一定の間隔（既定 920 MHz は 250 ms・2.4 GHz は 100 ms）で送ります。
- RX は、受け取ったパケットごとに受信レベルの生値を USB へ流します。PC 側の `python -m apps.field.cli record` がそれを記録します。
- 送受信のパケットと USB に流すデータの形は、どちらも `apps/field/mavlink/radiosim_field.xml` で定義しています。

ハードウェアは製品として配布しません。このファームは、測定に使う機材を再現できるようにするためにリポジトリで管理しています。

## 必要なもの

- Seeed Studio XIAO ESP32C6 × 2
- E220-900T22S(JP) × 2（版 2.0＝レジスタ `0x08` が `0x20`。違う版では設定を書かずに止まります）
- 技術基準適合証明の対象になっている 920 MHz 帯のアンテナ × 2
- 技術基準適合証明の対象になっている外付けの 2.4 GHz ロッドアンテナ（U.FL）× 2（2.4 GHz で測るとき）。2.4 GHz のとき、ファームは起動時にアンテナの切り替えを外付け側に固定します
- ESP-IDF **v6.1**（公式のインストーラ）。ほかの版ではビルドが止まります。測定記録に残るのはファームのコミットだけなので、同じコミットを別の版でビルドできてしまうと、記録から見分けられなくなるためです。版を上げるときは、`CMakeLists.txt` の `RADIOSIM_FIELD_IDF_VERSION` とこの行を直してコミットしてください。

### 配線

| XIAO のピン | E220 のピン |
|---|---|
| D0（GPIO0・UART1 TX） | RXD |
| D1（GPIO1・UART1 RX） | TXD |
| D2（GPIO2） | M0 |
| D3（GPIO21） | M1 |
| D10（GPIO18） | AUX |

UART は 9600 bps です。ピンは `main/e220.c` の先頭で定義しています。

## ビルドと書き込み

ESP-IDF のコマンドプロンプトで、このフォルダから実行します。

```
idf.py set-target esp32c6
idf.py build
idf.py -p COM5 flash
```

- ファームの版として git のコミット（10 桁）を焼き込みます。版はビルドのたびに取り直すので、コミットを進めたあとは `idf.py build` だけで新しい版になります（`idf.py reconfigure` は要りません）。作業ツリーに未コミットの変更があると、末尾に `-dirty` が付きます。測定に使うファームは、コミットしてからビルドしてください。
- git のコミットが取れない場所ではビルドが止まります（版の分からないファームは測定記録に残せないため）。
- `sdkconfig.defaults` を直したときは、このフォルダの `sdkconfig` を消してからビルドしてください。`sdkconfig` に既にある値は、`sdkconfig.defaults` より優先されます。
- ビルドのたびに、`sdkconfig.defaults` の各行が `sdkconfig` にそのまま入っているかを確かめます。食い違っているとビルドが止まり、食い違った項目が表示されます。`sdkconfig` は git で管理していないので、古い設定のまま焼いても、ファームの版（コミット）からは見分けられないためです。`menuconfig` で試しに変えた項目も、`sdkconfig.defaults` にある項目なら止まります。

`radiosim_field_mavlink.h` は生成物です。手で編集せず、XML を直したらリポジトリの直下で作り直します。

```
python -m apps.field.mavlink.gen_c
```

## 設定を変える

設定の表示と変更は、リポジトリの直下で CLI の `settings` から行います。

```
python -m apps.field.cli settings --port COM4
python -m apps.field.cli settings --port COM4 --role tx --channel 6 --power 10
python -m apps.field.cli settings --port COM4 --band 2400 --channel 1 --power 15
```

オプションを付けなければ、今の設定を表示するだけです。オプションを付けると 1 つずつ送り、再起動した機器から届いた設定を読み直して、実際に変わったことを確かめてから次へ進みます。範囲の外の値は、機器に送る前に止めます。帯域は最初に、役割は最後に変えます。使えるオプションは `--band 920|2400`・`--role tx|rx`・`--channel N`・`--interval MS`・`--power DBM` で、範囲は下の表と同じです。`--band` を省略すると、チャネル・間隔・電力は機器の今の帯域の範囲で確かめます。

機器の側は、USB シリアルに 1 行ずつ届くコマンド（行末は改行）を受け付けます。設定はフラッシュに保存され、変えると再起動します。USB にはバイナリのデータも流れているので、ターミナルソフトから手で打つと返答が読みにくく、`settings` を使うほうが確実です。

| コマンド | 内容 |
|---|---|
| `show` | 今の設定をすぐに送る |
| `role tx` / `role rx` | 送信か受信か（既定は受信） |
| `band 920` / `band 2400` | 測る帯域（既定は 920）。起動時にこの帯域だけを起こす |
| `channel N` | 今の帯域のチャネル。920 MHz は 0〜6（既定 0）で、周波数は 920.8＋0.2·N MHz。2.4 GHz は 1〜13（既定 1） |
| `interval MS` | 今の帯域の送信の間隔。920 MHz は 250〜10000 ms（既定 250）、2.4 GHz は 20〜10000 ms（既定 100） |
| `power DBM` | 今の帯域の送信電力。920 MHz は 0〜13 dBm・1 dB 刻み（既定 13）、2.4 GHz は 2〜20 dBm・0.25 dB 刻み（既定 15） |
| `cont SEC` | 連続送信を SEC 秒（1〜600）行い、終わったら再起動する。`cont 0` で中止。2.4 GHz の TX だけ。保存はしない |

- 役割・帯域・設定番号は 2 帯域で共通です。チャネル・間隔・電力は帯域ごとに別に保存するので、帯域を切り替えても、もう一方の帯域の値は残ります（NVS の名前空間は共通が `fieldcmn`、帯域ごとが `field920` と `field2400`）。
- 帯域を分ける前のファーム（920 MHz だけ）から書き換えると、役割と設定番号をそのとき保存されていた値から引き継ぎます。設定番号は 1 つ進みます（欠けた値を既定値で埋めたため）。2.4 GHz だけだった頃のファームの設定は引き継ぎません。

- 設定を変えるたびに設定番号（`config_id`）が 1 つ進みます。PC 側は番号でサンプルと設定を結びつけるので、同じ番号が別の設定を指すことはありません。
- TX と RX は同じ帯域・同じチャネルに合わせてください。TX は自分の設定を空中へも送り（920 MHz は 10 秒ごと、2.4 GHz は 1 秒ごと）、RX がそれを USB へ中継します。PC 側は TX の設定を中継されたものから取るので、雛形（JSON）には TX の無線設定を書きません。920 MHz で 10 秒ごとなのは、1 秒ごとだと送信時間の割合が 10% を超えるためです。そのぶん、PC が記録を始めるまで最長 10 秒待ちます。
- 設定の欄のうち、その帯域に無いものは 0 です（920 MHz は `rate_kbps`、2.4 GHz は `air_sf`・`air_bw_khz`）。

## 連続送信（送信電力を測るとき・2.4 GHz だけ）

普段の TX は 100 ms ごとに短いパケットを送るだけなので、平均電力計で測ると実際の送信電力より 15 dB ほど低く出ます。`cont SEC` は、普段と同じ送信の経路と同じ電力の設定のまま、最も長いフレーム（1500 バイト・1 Mbps で約 12 ms）を間を詰めて送り続けます。

- フレームの間には必ず隙間が空くので、ファームは送信完了の時刻から実際の送信時間の割合（デューティ）を測り、1 秒ごとに `CONT duty=… intervals=… other_rate=… …` の行で知らせます。バースト中の電力は「平均電力計の読み − 10·log10(デューティ)」です。`python -m apps.field.cli cont` がこの計算と記録を行います（`BENCH.md` のステージ0b）。
- `other_rate` が 0 でないときは、1 Mbps 以外で出たフレームがあったのでデューティを使えません。
- 始める前に設定番号（`config_id`）を 1 つ進め、終わったら再起動します。連続送信の間は番号付きのパケットも設定も送らないので、この間を跨いだ記録は、再起動後の新しい設定番号で PC 側が閉じます。
- 設定は保存しません。電源を入れ直せば普段の送信に戻ります。
- PHY の試験モード（連続波など）は使っていません。電力の指定の経路が普段の測定と違い、測った値が測定に使う出力と同じである保証が無いためです。
- 920 MHz では使えません。E220 は送信している間を外へ知らせない（AUX が Low の時間は空中に電波が出ている時間と一致しない）ので、デューティを測れないためです。920 MHz のときに `cont` を送ると `ERR cont は 2.4 GHz だけです（band 2400 にしてから）` が返ります。

## 空中の設定（920 MHz）

空中の拡散率と帯域幅（SF7・500 kHz）はファームの定数で、設定では変えられません（`main/e220.h` の `E220_AIR_SF`・`E220_AIR_BW_KHZ`）。設定の `air_sf`・`air_bw_khz` はこの定数を写したものです。

起動すると、自己検査の後にモジュールの設定（レジスタ `0x00`〜`0x0A`）を書き、読み直して照らし合わせます。モジュールの版が違う・書いた値と読めた値が食い違うといった場合は測定を始めず、`ERR <理由>（読めた値 …）` を 1 秒ごとに送ります。この状態でもコマンドは受け付けるので、`role rx` などで抜けられます。

TX は、周期の頭でモジュールが送信できる状態か（AUX が High か）を見て、送れないときはその周期を送りません。前の周期の送信がキャリアセンスで阻まれたかどうかも、ここでモジュールに問い合わせます。送らなかった周期はパケットの `sent_mask`（直前 32 周期）と `unsent_total`（起動からの累計）に残るので、PC 側は「送らなかった」を「受からなかった」と数えずに済みます。

## USB に流れるもの

- 設定（`RADIOSIM_FIELD_CONFIG`）：起動時と変更時に加えて、1 秒ごとに送ります。PC 側は同じ設定の再送を読み飛ばすので、RX を先に起動しておいても記録を始められます。RX は、空中で受けた TX の設定もそのまま流します。
- 受信サンプル（`RADIOSIM_FIELD_RX_SAMPLE`、RX のみ）：受信 1 回ごと。受信レベルと、その時点の雑音の生値を載せます。送信機ごとの通し番号（`sample_seq`）を受信した時点で振るので、USB への書き込みやキューで落ちたサンプルは、PC 側で番号の欠けとして分かります。電波で届かなかったパケットには番号が振られないため、この 2 つは区別できます。受けたパケットの `sent_mask`・`unsent_total` の写しも載せます（TX の USB は現場で PC に繋がらないため）。
- 送信の控え（`RADIOSIM_FIELD_TX_PACKET`、TX のみ）：送信の周期ごと。
- コマンドへの返答（`OK ...` / `ERR ...` のテキスト行）と、連続送信の報告（`CONT ...` のテキスト行）。

ログは USB ではなく UART0 のピンに出します。ログの行がデータの途中に割り込むと、そのデータは PC 側で壊れたものとして捨てられ、電波が届かなかった場合と区別できなくなるためです。

起動すると、まず自己検査をします。組み立てたデータが PC 側と 1 バイトでも食い違うと、`ERR 自己検査に落ちました` を 1 秒ごとに送るだけで、測定は始めません。

1 台の実機（2026-09-19）で確かめたこと:

- USB のポートを閉じるとボードがリセットされます。開いたときはリセットされません。
- ポートを開いた直後に最初に届くデータは、閉じていた間に溜まっていた古いものです。

## 空中のレート（2.4 GHz）

空中のレートは 1 Mbps（11b・ロングプリアンブル）に固定しています。TX は起動するたびに確認用のフレームを 1 つ送り、無線のドライバが実際に使ったレートを確かめます。1 Mbps でなければ測定を始めず、`ERR 空中のレートが 1 Mbps になりません（実際 … kbps・0＝不明）` を 1 秒ごとに送ります。この状態でもコマンドは受け付けるので、`role rx` などで抜けられます。

測定の途中でレートが変わった場合、TX は送信を止めません。止めると、RX には電波が届かなくなったのと同じに見えるためです。代わりに、設定の `rate_kbps` を実際の値に直してすぐに送ります。PC は設定が変わったのを見て、そこでセッションを閉じます。

空中に送るパケットの識別子（`main/radio_wifi.c` の `RADIOSIM_FIELD_AIR_OUI`）は仮の値で、登録された値ではありません。

2.4 GHz だけで送受信していた版（帯域を分ける前）の実機の記録は、git の履歴（`8923e90` の README）にあります。帯域を分けた今のファームでは、2.4 GHz の実機の確認はまだです。
